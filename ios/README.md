# RescueMesh iPhone app — Mac handoff

Native SwiftUI app targeting **iOS 17+**, with a portable Xcode project, XCTest target and **Temoc**, an on-device chat assistant. Temoc uses the local `TemocRuntime` Swift package and the checksum-pinned official **llama.cpp b5046** XCFramework. No CocoaPods, XcodeGen, chat API key or cloud inference account is required. Source preparation and packaging on Windows do not prove Xcode compilation, simulator layout, signing, model performance or physical BLE operation; inspect the dated `verification.json` receipts and run the Mac checks below.

## Open on a Mac

1. Extract `RescueMesh-Mac.zip`. In Terminal, enter the extracted `RescueMesh-Mac` folder and run `bash scripts/prepare-mac.sh --open`. The script verifies the bundled official framework archive, restores the XCFramework with macOS `ditto` so its framework symlinks remain valid, then opens `EmergencyMesh.xcodeproj`. The default handoff does not bundle model weights; download those once inside the installed app. Use full Xcode 16+ with an iOS 17+ SDK. Run this preparation **before** Xcode resolves the local package. Do not substitute a framework copied from a Windows extraction.
2. Select the **EmergencyMesh** scheme. The installed app is named **RescueMesh**; project and target names stay compatible with the existing handoff. Select an iPhone simulator and Run to inspect Report, My requests, Temoc and Setup. Setup → Local radio-free check → **Check encryption locally** exercises encryption/chunk reassembly using public synthetic data. It never writes to BLE or creates a confirmed request.
3. For a real iPhone, select the EmergencyMesh target → Signing & Capabilities → choose your own development Team, change `org.hackutd.EmergencyMesh` to a unique bundle identifier if necessary, keep automatic signing enabled, then select the connected phone. Enable Developer Mode on that phone if Xcode requests it. The unsigned ZIP is source, not an installable IPA.
4. Import the **private provisioning JSON** created by the hub's provisioning command through Files, or paste it in Setup's secure field. Shape: `{ "region": 1, "keyId": 1, "keyHex": "<64 hexadecimal characters>", "origin": 123456789 }`. Each newly enrolled phone has a different nonzero `origin` and independent random 256-bit content key. The hub stores the enrolled keys; relays and companion firmware do not. The demo's radio firmware uses key slot `1` for all phones; that slot is an identifier, not a shared key. Existing shared-key profiles work only after explicit hub registration and should be replaced with independently keyed profiles. Do not use the public test key from XCTest for actual reports. The app stores the profile in Keychain; no private key is compiled into the firmware or app.
5. Flash companion firmware on your board and confirm the correct frequency/matching antenna. Power it from the USB-C adapter/cable or a suitable independent supply. The USB cable provides power; phone app data uses BLE. Confirm actual phone power stability before relying on this arrangement.
6. Report → Connect your companion → Find nearby companions → select your team's board. **Connected** is shown only after UART characteristics are discovered and receipt notifications are enabled. Grant Bluetooth access. The reporting form automatically requests location authorization and refreshes GPS while visible; every send includes the freshest available valid fix. A missing fix does not block sending.
7. On the same reporting form, enter the reported danger, priority, people count, supplies and at most 120 UTF-8 bytes of details/landmark, then tap **Send**. There is no separate review screen. When disconnected, saving a request keeps it queued. The receipt screen and My requests show its actual delivery state. A completed BLE transfer means **Waiting for the hub**. Only an authenticated receipt for this phone's origin and an existing request changes it to **Received by the hub** or **Operator reviewed**. Neither confirms emergency-service dispatch. Transport counters and receipt text are inside **Delivery details**.

The default ZIP uses **download once in the app**: it includes the untouched 74,944,281-byte llama.cpp archive but omits the 1,117,320,736-byte Qwen2.5 1.5B Q4_K_M model. Expect a handoff around 77 MB. After installing, open **Temoc → Set up → Download model over Wi-Fi**. The app verifies the model's exact size and SHA-256, saves it on the phone, and then runs chat offline without downloading it again. Saved guides work before the model is installed. The separate `RescueMesh-Mac-SourceOnly.zip` and public Git source omit the framework archive too, so Xcode needs internet once to fetch that checksum-pinned runtime. An optional `RescueMesh-Mac-Offline.zip`, built with `-BundleModel`, includes the model for an explicitly requested full offline handoff. Xcode, its SDK/simulator components and a development signing identity must already be available on the Mac for an offline build/device install.

## Temoc model and chat

Open Temoc to start a new chat, revisit separate local conversations, use saved guides or manage the model. In **Set up**, choose **Download model over Wi-Fi** once, or explicitly import the pinned model file. Installation checks exact length and SHA-256 before persisting the file in the phone's protected `Application Support/TemocModels/` directory; later launches discover the installed model. Open-ended replies then use local llama.cpp inference with a 2,048-token context and bounded reply length. Recent messages fit into each prompt; earlier messages remain in history. No chat API receives messages, GPS or phone provisioning keys. Model inference speed, memory use and output quality still require a real-device check.

Pinned model: `Qwen/Qwen2.5-1.5B-Instruct-GGUF`, revision `91cad51170dc346986eccefdc2dd33a9da36ead9`, filename `qwen2.5-1.5b-instruct-q4_k_m.gguf`, SHA-256 `6a1a2eb6d15622bf3c96857206351ba97e1af16c30d7a74ee38970e434e9407e`. Runtime archive SHA-256: `c19be78b5f00d8d29a25da41042cb7afa094cbf6280a225abe614b03b20029ab`. Both licenses accompany the source in `TemocRuntime/`.

Chats are encrypted on this phone, excluded from backups and covered when inactive. Temoc has no radio/dispatcher tools and cannot submit a report, contact help or establish that a situation is safe. Selected high-risk prompts route to saved guidance, and generated text is screened for certain medication and dispatch claims. These bounded safeguards do not establish clinical validity or guarantee safe model output. Use the Report flow for an actual mesh request; no chat reply changes delivery state.

## Mac verification

From this `ios` directory:

```bash
bash scripts/check-mac.sh
xcrun simctl list devices available
SIMULATOR_ID=<an-installed-iPhone-simulator-UDID> bash scripts/check-mac.sh --test
```

Run `bash scripts/prepare-mac.sh` first. The check script lints the plist/project, lists the Xcode targets and builds without device signing. With `--test` it runs XCTest on an explicitly selected installed simulator. `WireCodecTests.swift` contains the 20 protocol/storage tests; `TemocSafetyTests.swift` adds four tests for guidance routing, output screening, likely-key rejection and separate bounded chat storage. Their execution is a native Mac check, separate from Windows source/package validation. The public cross-language fixture is `EmergencyMeshTests/golden-v1.json`. Xcode's Test action is an alternative.

Inspect the single Report form, receipt, My requests, Temoc and Setup on a small iPhone and at larger Dynamic Type sizes; check draft preservation, dark mode, denied permissions, Bluetooth off, no device, connection loss during transfer, keyboard scrolling, explicit retry after unconfirmed status, relaunch with a queued request, and GPS older than 2 minutes. For Temoc, complete the one-time download, relaunch and verify a real generated reply in Airplane Mode; also test stop/cancel, new-chat separation, relaunch history, missing/corrupt model handling and the saved-guide routes. A simulator does **not** validate physical BLE, antenna/radio coverage, iPhone USB power, on-device inference performance or background reliability.

## Delivery and privacy behavior

Drafts and outbox (including the original encrypted radio bytes) are AES-GCM encrypted at rest with a random Keychain local key. The directory is excluded from app backups and uses iOS file protection. Sensitive content is covered when the app is inactive. Clear local history and key removes this phone's stored requests and profile; it cannot remove incidents already received by a hub. Nonsecret identity sequence counters remain in Keychain so reimporting the same profile does not reuse a hub replay ID. Those counters reserve each sequence before any send and survive ordinary reinstalls when Keychain is retained. If the phone is erased or Keychain is reset, provision a fresh phone origin instead of reusing an old profile. Replacing a profile while requests remain is refused so old receipts cannot be mistaken for a new profile's status.

Retries reuse identical encrypted bytes at approximately 10, 25 and 45 seconds after the first attempt, with a minimum 8-second gap when resuming delayed work. After the final attempt's receipt window (55 seconds from first send), status becomes **Delivery unconfirmed**. An explicit retry restarts this bounded sequence. Requests queued while disconnected remain on this phone. Keep the app open during the demonstration: iOS background execution is opportunistic, and timers are not guaranteed while suspended. BLE state restoration and an encrypted outbox support later resume; they do not promise continuous background delivery.

Position is included only if valid and captured within 2 minutes of queuing, with accuracy and request creation time in the packet. Otherwise the payload explicitly means unknown GPS; describe landmarks in the short note. Category/priority and special-condition flags are user reported; the app does not provide medical triage. Independently keyed phones cannot decrypt each other's reports or receipts. A copied private profile clones that identity, and a compromised hub can read the region's reports. Legacy shared-key holders can still read/impersonate other explicitly enrolled legacy identities until those profiles are replaced. Visible relay metadata and traffic remain observable. A SHA-256 fingerprint identifies a key; it is neither the secret nor proof of a physical board. This is not an emergency-service connection. The hub's `docs/device-security.md` describes enrollment, wrapped storage and revocation.

## Files and design evidence

`EmergencyMesh/` contains 13 app Swift files, the native `RescueMesh.xcassets` catalog and public model metadata. Model weights are absent from the default handoff and included only in the optional `-BundleModel` handoff. `EmergencyMeshTests/` contains the protocol and Temoc tests. `TemocRuntime/Package.swift` selects the restored local XCFramework when present and otherwise resolves the pinned official archive; its `Sources/` contains the runtime and Mac smoke executable. `scripts/create-project.mjs` reproduces the checked-in project with Node if source files are intentionally added/removed; ordinary Mac users need not run it. The shared scheme and source paths are relative to the ZIP root.

The current Temoc concept is `design/temoc-target.png`; the earlier request-flow concept is `design/rescuemesh-phone.png` (1670×941). Native PDF/PNG logo assets and the magenta `#E20074` accent live in `RescueMesh.xcassets`. Report, My requests, Temoc and Setup use native navigation. A reported landmark stays in the user's note; the UI never invents a location from arbitrary text. Generated concepts are design evidence; visual fidelity, Dynamic Type and keyboard behavior require actual simulator/device captures.

Primary API references: [Core Bluetooth restoration](https://developer.apple.com/documentation/corebluetooth/cbcentralmanageroptionrestoreidentifierkey), [notification-state callback](https://developer.apple.com/documentation/corebluetooth/cbperipheraldelegate/peripheral(_:didupdatenotificationstatefor:error:)), [background constraints](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html).
