# RescueMesh iPhone app — Mac handoff

Native SwiftUI app targeting **iOS 17+**, with a portable Xcode project and XCTest target. No CocoaPods, XcodeGen, API key, cloud account or third-party Swift dependency. Source and project were prepared on Windows; **Xcode compilation, simulator layout, signing and physical BLE operation still need the Mac checks below**. A checked-in project or source parse does not prove those checks pass.

## Open on a Mac

1. Extract the handoff ZIP. Open `EmergencyMesh.xcodeproj` in full Xcode 16+ (or newer with an iOS 17+ SDK). Trust only your own checkout; no package-install script is required.
2. Select the **EmergencyMesh** scheme. The installed app is named **RescueMesh**; project and target names stay compatible with the existing handoff. Select an iPhone simulator and Run to inspect screens. Setup → Local radio-free check → **Check encryption locally** exercises encryption/chunk reassembly using public synthetic data. It never writes to BLE or creates a confirmed request.
3. For a real iPhone, select the EmergencyMesh target → Signing & Capabilities → choose your own development Team, change `org.hackutd.EmergencyMesh` to a unique bundle identifier if necessary, keep automatic signing enabled, then select the connected phone. Enable Developer Mode on that phone if Xcode requests it. The unsigned ZIP is source, not an installable IPA.
4. Import the **private provisioning JSON** created by the hub's provisioning command through Files, or paste it in Setup's secure field. Shape: `{ "region": 1, "keyId": 1, "keyHex": "<64 hexadecimal characters>", "origin": 123456789 }`. Each newly enrolled phone has a different nonzero `origin` and independent random 256-bit content key. The hub stores the enrolled keys; relays and companion firmware do not. The demo's radio firmware uses key slot `1` for all phones; that slot is an identifier, not a shared key. Existing shared-key profiles work only after explicit hub registration and should be replaced with independently keyed profiles. Do not use the public test key from XCTest for actual reports. The app stores the profile in Keychain; no private key is compiled into the firmware or app.
5. Flash companion firmware on your board and confirm the correct frequency/matching antenna. Power it from the USB-C adapter/cable or a suitable independent supply. The USB cable provides power; phone app data uses BLE. Confirm actual phone power stability before relying on this arrangement.
6. Request → Connect your companion → Find nearby companions → select your team's board. **Connected** is shown only after UART characteristics are discovered and receipt notifications are enabled. Grant Bluetooth access. Choose **Use current location** on the details screen to opt into location access; a recent GPS fix is optional.
7. Select a category → Continue → enter your reported priority, people count and at most 120 UTF-8 bytes of details/landmark → Review request → Send request. When disconnected, **Save request to send** keeps it safely queued. The receipt screen and **My requests** show its actual delivery state. A completed BLE transfer means **Waiting for the hub**. Only an authenticated receipt for this phone's origin and an existing request changes it to **Received by the hub** or **Operator reviewed**. Neither confirms emergency-service dispatch. Transport counters and receipt text are inside **Delivery details**.

## Mac verification

From this `ios` directory:

```bash
bash scripts/check-mac.sh
xcrun simctl list devices available
SIMULATOR_ID=<an-installed-iPhone-simulator-UDID> bash scripts/check-mac.sh --test
```

The script lints the plist/project, lists the Xcode targets and builds without device signing. With `--test` it runs the XCTest target on an explicitly selected installed simulator. The 14 authored tests compare Swift CryptoKit with the Node golden request/receipt, reject sibling keys, wrong recipients, header tampering and wrong regions/types, check mutable relay hops, UTF-8 limits, old/unknown GPS, durable counters, saved retry frames and chunk reassembly/timeout. These XCTest methods have not been executed on this Windows host. The public test fixture is `EmergencyMeshTests/golden-v1.json`. Xcode's Test action is an alternative.

Inspect category selection, details, review, receipt, My requests and Setup on a small iPhone and at larger Dynamic Type sizes; check Back preserves the draft, dark mode, denied permissions, Bluetooth off, no device, connection loss during transfer, keyboard scrolling, explicit retry after unconfirmed status, relaunch with a queued request, and GPS older than 2 minutes. A simulator does **not** validate physical BLE, antenna/radio coverage, iPhone USB power or background reliability.

## Delivery and privacy behavior

Drafts and outbox (including the original encrypted radio bytes) are AES-GCM encrypted at rest with a random Keychain local key. The directory is excluded from app backups and uses iOS file protection. Sensitive content is covered when the app is inactive. Clear local history and key removes this phone's stored requests and profile; it cannot remove incidents already received by a hub. Nonsecret identity sequence counters remain in Keychain so reimporting the same profile does not reuse a hub replay ID. Those counters reserve each sequence before any send and survive ordinary reinstalls when Keychain is retained. If the phone is erased or Keychain is reset, provision a fresh phone origin instead of reusing an old profile. Replacing a profile while requests remain is refused so old receipts cannot be mistaken for a new profile's status.

Retries reuse identical encrypted bytes at approximately 10, 25 and 45 seconds after the first attempt, with a minimum 8-second gap when resuming delayed work. After the final attempt's receipt window (55 seconds from first send), status becomes **Delivery unconfirmed**. An explicit retry restarts this bounded sequence. Requests queued while disconnected remain on this phone. Keep the app open during the demonstration: iOS background execution is opportunistic, and timers are not guaranteed while suspended. BLE state restoration and an encrypted outbox support later resume; they do not promise continuous background delivery.

Position is included only if valid and captured within 2 minutes of queuing, with accuracy and request creation time in the packet. Otherwise the payload explicitly means unknown GPS; describe landmarks in the short note. Category/priority and special-condition flags are user reported; the app does not provide medical triage. Independently keyed phones cannot decrypt each other's reports or receipts. A copied private profile clones that identity, and a compromised hub can read the region's reports. Legacy shared-key holders can still read/impersonate other explicitly enrolled legacy identities until those profiles are replaced. Visible relay metadata and traffic remain observable. A SHA-256 fingerprint identifies a key; it is neither the secret nor proof of a physical board. This is not an emergency-service connection. The hub's `docs/device-security.md` describes enrollment, wrapped storage and revocation.

## Files and design evidence

`EmergencyMesh/` contains the app, codec, BLE transport, location and protected storage. `EmergencyMeshTests/` contains cross-language tests. `scripts/create-project.mjs` reproduces the checked-in project with Node if source files are intentionally added/removed; ordinary Mac users need not run it. The shared scheme and source paths are relative to the ZIP root.

The current generated design reference is `design/rescuemesh-phone.png`, actually 1670×941 pixels, showing the Ask → Send → Wait flow in three phone panels. It was inspected before this update. The implementation uses the selected categories, bold native titles, white/system surfaces and T-Mobile-inspired `#E20074` actions. Details have a separate native form, with GPS and additional concerns available when needed. My requests and Setup complete the application. A reported landmark stays in the user's note; the UI never invents a location from arbitrary text. Three native tabs are a navigation adaptation to the concept. The older orange `design/request-target.png` remains historical evidence. No native simulator/device capture exists yet, so visual fidelity, Dynamic Type and keyboard behavior remain unverified.

Primary API references: [Core Bluetooth restoration](https://developer.apple.com/documentation/corebluetooth/cbcentralmanageroptionrestoreidentifierkey), [notification-state callback](https://developer.apple.com/documentation/corebluetooth/cbperipheraldelegate/peripheral(_:didupdatenotificationstatefor:error:)), [background constraints](https://developer.apple.com/library/archive/documentation/NetworkingInternetWeb/Conceptual/CoreBluetooth_concepts/CoreBluetoothBackgroundProcessingForIOSApps/PerformingTasksWhileYourAppIsInTheBackground.html).
